# GNWES ↔ real Kubernetes DRA + CDI

This replaces the simulated "sleep standing in for attach" with the real
mechanism: a genuine `resource.k8s.io/v1` `ResourceClaim`, allocated by the
real Kubernetes scheduler against a real `ResourceSlice`, resolved by a real
DRA kubelet plugin (`cmd/mock-gpu-driver`) that writes a real CDI spec file,
which containerd genuinely injects into the container. Only the device
identity is fake — there is no real NVIDIA GPU in this environment, so the
"device" the CDI spec exposes is a container environment variable
(`GNWES_MOCK_GPU_SLOT`), clearly labeled as a stand-in, not real hardware.

This is additive and separate from the existing simulated-attach demo
(`cmd/manager` + `internal/controller`/`internal/pool`, and the Substrate
integration in `config/substrate-integration`) — nothing there was changed.
It is a second, independent proof that the real DRA+CDI mechanism works, built
directly on `k8s.io/dynamic-resource-allocation` (the same helper library a
real GPU vendor's driver would use), not a replacement for the admission-gate
demo.

## What's real vs mocked

| Layer | This build |
|---|---|
| `DeviceClass`, `ResourceClaimTemplate`, `ResourceClaim` objects | **Real** K8s API objects |
| Scheduling/allocation (pod won't run until a device is actually allocated) | **Real** — native `kube-scheduler` DRA allocation, not a GNWES mechanism |
| `ResourceSlice` publication (how the driver advertises devices) | **Real** — via `k8s.io/dynamic-resource-allocation/resourceslice`, the same helper a real driver uses |
| Kubelet plugin registration + `PrepareResourceClaims`/`UnprepareResourceClaims` gRPC | **Real** — via `k8s.io/dynamic-resource-allocation/kubeletplugin` |
| CDI spec file written to `/etc/cdi` and loaded by containerd | **Real** file, real containerd CDI injection (confirmed: `enable_cdi = true`, `cdi_spec_dirs = ['/etc/cdi', '/var/run/cdi']` on this node by default in containerd 2.x) |
| The device itself | **Mocked.** `ContainerEdits.Env` sets `GNWES_MOCK_GPU_SLOT=<name>` — no real NVIDIA device node, driver, or silicon involved |

## A real gap this surfaced in Agent Substrate

Checked whether a real Substrate `WorkerPool` pod could declare this
`ResourceClaimTemplate` directly (so the GPU-attached warm-pod story from
`config/substrate-integration` could use real DRA instead of GNWES's own
simulated pool). It cannot, today: `WorkerPoolPodTemplate`
(`agent-substrate/substrate`'s `api/infra/k8s/ate/v1/workerpool_types.go`) has
no `resourceClaims` field, and the controller code that maps pod-template
settings onto the generated pod
(`cmd/atecontroller/internal/controllers/workerpool_apply.go`, function
`applyWorkerPoolPodTemplate`, ~lines 583-609) only ever sets
`NodeSelector`/`Tolerations`/`PriorityClassName`/`ServiceAccountName`/
`NodeAffinity` — never `pod.spec.resourceClaims`. This build therefore proves
the DRA+CDI mechanism against a plain GNWES-created test pod
(`test-pod.yaml`), not a real Substrate worker pod.

**This is a known, open gap upstream, not just something this build found.**
Substrate's own Nov 2026 announcement
([blog](https://developer.nvidia.com/blog/agent-substrate-advancing-kubernetes-for-agents-at-scale/))
says plainly: "GPU support is being rebuilt on the new DRA foundation," and
device pluggability via DRA is tracked only as an open design issue
([#752](https://github.com/agent-substrate/substrate/issues/752)), not a
merged PR. The deeper reason it's unsolved isn't the missing
`resourceClaims` field — that's a small API gap, easy to add — it's that
vanilla Kubernetes DRA resolves a `ResourceClaim` at pod *creation* time, full
stop, while Substrate's whole model is reusing one already-running worker pod
across many sequential actors (`WorkerPool` multiplexes actors onto a small,
long-lived pool rather than creating a pod per actor). Wiring real DRA onto a
`WorkerPool` pod template would get you a GPU attached once, at that pod's
creation — not attached/detached per actor turn, which is what Substrate
actually needs. That deeper mismatch is what this build leaves open, same as
upstream's own roadmap. See `config/substrate-integration/README.md` for
exactly how far GNWES's own gating/leasing goes against a real `WorkerPool`
today, and what it still doesn't attempt.

## Running on real GPU nodes

The DRA/CDI mechanism above (`ResourceClaim` allocation, the kubelet plugin
protocol, CDI injection) doesn't change when real hardware is involved — only
how devices are discovered and what the CDI spec actually edits does. That's
now a second backend in `cmd/mock-gpu-driver`, selected by the
`GNWES_GPU_BACKEND` env var:

| | `GNWES_GPU_BACKEND=mock` (default) | `GNWES_GPU_BACKEND=nvidia` |
|---|---|---|
| Device discovery | 4 hardcoded fake devices | Real GPUs via `nvidia-smi --query-gpu=...` (`cmd/mock-gpu-driver/nvidia.go`) |
| CDI spec | Hand-written by this driver; only edit is an env var | Either generated by `nvidia-ctk cdi generate` itself, or (more commonly) reused from one an already-running GPU-management system maintains — see `NVIDIA_CDI_MODE` below |
| What gets injected into the container | `GNWES_MOCK_GPU_SLOT=<name>` env var | Real device nodes, driver library mounts, and env vars for an actual GPU |

The `nvidia` backend itself has a further choice, `NVIDIA_CDI_MODE`:

- **`existing`** — reuse a CDI spec some other, already-running system
  manages. The common real-world case: a node already running **NVIDIA GPU
  Operator** with CDI enabled (`ClusterPolicy.spec.cdi.enabled: true`)
  already has its own device plugin writing a fully correct, hook-laden spec
  to `/var/run/cdi` as part of normal operation — reuse that instead of
  generating a second, redundant one. This mode needs no `nvidia-ctk` access
  at all; `driver-real-gpu.yaml` defaults to it. Point
  `NVIDIA_CDI_EXISTING_SPEC`/`NVIDIA_CDI_KIND` at your file/kind if they
  differ (check `ls /var/run/cdi` and the `"kind"` field inside the file —
  GPU Operator's own device plugin typically names it
  `k8s.device-plugin.nvidia.com-gpu.json` with kind
  `k8s.device-plugin.nvidia.com/gpu`, which are this mode's defaults).
- **`generate`** (default if `NVIDIA_CDI_MODE` is unset) — call
  `nvidia-ctk cdi generate` itself. For a node with the NVIDIA driver and
  `nvidia-container-toolkit` installed directly (no GPU-management operator
  running). See the commented alternative in `driver-real-gpu.yaml` for the
  mounts this needs instead.

**Prerequisites on the GPU node** (standard for any Kubernetes GPU node, not
GNWES-specific):
- An NVIDIA driver installed, such that `nvidia-smi` on the host lists your
  GPU(s).
- Either NVIDIA GPU Operator already running with CDI enabled (`existing`
  mode), or `nvidia-container-toolkit` installed directly (`generate` mode)
  — and the CRI (containerd or CRI-O) configured to watch `/etc/cdi` /
  `/var/run/cdi`, which either install path normally does by default.
- The node labeled so the DaemonSet lands only on GPU nodes —
  `driver-real-gpu.yaml` defaults to `nvidia.com/gpu.present: "true"` (what
  NVIDIA GPU Feature Discovery / GPU Operator set automatically); label
  manually if you run neither:
  `kubectl label node <gpu-node> nvidia.com/gpu.present=true`.

Genuine Kubernetes DRA hands CDI device IDs to the container runtime through
the CRI's own `CDIDevices` field, independent of any `RuntimeClass` a
classic device-plugin setup might also have configured (e.g. GPU Operator's
`nvidia`/`nvidia-cdi`/`nvidia-legacy` runtime classes) — no `runtimeClassName`
is needed on the driver pod or test pod here.

**Reproducing this:**

```bash
# Build the real-GPU image (needs a real libc/dynamic linker to exec the
# host-mounted nvidia-smi binary, unlike the mock image's distroless/static
# base):
docker build --target real-gpu -t <your-registry>/gnwes-mock-gpu-driver:real-gpu -f cmd/mock-gpu-driver/Dockerfile .
docker push <your-registry>/gnwes-mock-gpu-driver:real-gpu
```

Update the `image:` field in `driver-real-gpu.yaml` to match, then:

```bash
kubectl apply -f deviceclass.yaml               # unchanged, same DeviceClass
kubectl apply -f driver-real-gpu.yaml           # instead of driver.yaml
kubectl apply -f resourceclaimtemplate.yaml     # unchanged
kubectl apply -f test-pod-real-gpu.yaml         # instead of test-pod.yaml

kubectl get resourceclaim -n gnwes-dra-demo -o wide
kubectl get pod gnwes-dra-test-real-gpu -n gnwes-dra-demo
kubectl logs -n gnwes-dra-demo -l app=gnwes-mock-gpu-driver-real --tail=20

# The real proof: a real NVIDIA device actually usable inside the container.
kubectl exec gnwes-dra-test-real-gpu -n gnwes-dra-demo -- nvidia-smi
```

Expect `nvidia-smi` inside the container to print your real GPU, not an
error — that's the DRA allocation + kubelet plugin + CDI injection chain
handing the container a real, working device.

**Shared-cluster note:** if other workloads on the same node already consume
GPUs through a classic device plugin (`nvidia.com/gpu` extended resource,
e.g. GPU Operator's default setup), that mechanism and this DRA driver don't
share bookkeeping — each thinks it owns the physical GPUs it can see.
Confirm there's free, actually-idle capacity (`nvidia-smi` showing no
running processes, `kubectl describe node <gpu-node>` for current
`nvidia.com/gpu` allocation) before testing on a node with other active
users, or test during a quiet window.

**Verified on real hardware:** this path (`NVIDIA_CDI_MODE=existing`) has
been run end-to-end on a real 3x NVIDIA TITAN RTX node managed by NVIDIA GPU
Operator (CRI-O runtime, CDI enabled via `ClusterPolicy`). Confirmed:
- the driver published all 3 real GPUs via `ResourceSlice`,
- a `ResourceClaim` reached `allocated,reserved` against driver
  `mock-gpu.gnwes.io`, device `gpu-0`,
- and — the real proof — `nvidia-smi` run inside the test pod showed
  **exactly the one GPU that claim was allocated** (matching PCI bus ID),
  not all three physical GPUs on the node. Real DRA allocation and real CDI
  device isolation, not just objects existing in etcd.

The `NVIDIA_CDI_MODE=generate` path (no GPU Operator, bare-metal
`nvidia-container-toolkit` install) is still unverified against real
hardware — it's code-reviewed and unit-tested the same way, but hasn't had
a matching cluster to run on.

## Reproducing this (mock backend, no hardware needed)

```bash
kubectl --context kind-kind apply -f deviceclass.yaml
kubectl --context kind-kind apply -f driver.yaml        # namespace, RBAC, DaemonSet
kubectl --context kind-kind apply -f resourceclaimtemplate.yaml
kubectl --context kind-kind apply -f test-pod.yaml

# Confirm the claim allocated and the pod actually runs only once it did:
kubectl --context kind-kind get resourceclaim -n gnwes-dra-demo -o wide
kubectl --context kind-kind get pod gnwes-dra-test -n gnwes-dra-demo

# Confirm the driver's PrepareResourceClaims actually ran:
kubectl --context kind-kind logs -n gnwes-dra-demo -l app=gnwes-mock-gpu-driver

# The real proof: exec into the running container and see the CDI-injected
# env var actually present (not just that objects exist in etcd):
kubectl --context kind-kind exec gnwes-dra-test -n gnwes-dra-demo -- env | grep GNWES_MOCK_GPU
```
